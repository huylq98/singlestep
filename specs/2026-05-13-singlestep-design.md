## 1. Goals and non-goals

### Primary goals (in priority order)

1. **For me first.** A personal knowledge home that I will actually use daily. Authoring must be frictionless; finding my own notes must be fast.
2. **For other engineers second.** Every page stands alone, is shareable, and is high-signal enough that someone arriving cold from a link bookmarks the site.
3. **Eventually authoritative.** Over time, become the go-to reference for the kinds of topics I cover — not by volume, but by depth and clarity. The interactive simulations are the moat.

### Non-goals (V1)

- A general blogging platform with comments, reactions, or social engagement features.
- A multi-author CMS.
- A multilingual site.
- A newsletter or subscription system beyond RSS.
- Server-side anything. The site is fully static.
- Analytics in V1.

## 2. Content model

Three top-level surfaces, all in the navbar:

| Surface     | Purpose                                                        | Path        | Format        |
| ----------- | -------------------------------------------------------------- | ----------- | ------------- |
| Docs (wiki) | Evergreen reference notes. Editable forever, no dates.         | `/docs/...` | `.md` / `.mdx` |
| Blog        | Dated narrative posts: stories, experiences, lessons learned.  | `/blog/...` | `.md` / `.mdx` |
| Playground  | A browsable gallery of every interactive simulation, by topic. | `/playground` | React page |

Plus:

- `/` — landing page (hero, featured sims, recent posts).
- `/about` — what this is and who I am. Required so a cold visitor can orient in 10 seconds.

### Three authoring patterns

| Pattern              | Where                                  | Format | Sims |
| -------------------- | -------------------------------------- | ------ | ---- |
| Quick note           | `docs/<topic>/<slug>.md`              | MD     | No   |
| Deep reference       | `docs/<topic>/<slug>.mdx`             | MDX    | Yes  |
| Story / experience   | `blog/YYYY-MM-DD-<slug>.mdx`          | MDX    | Often |

### Tagging

- Blog posts use a `tags` frontmatter field; Docusaurus auto-generates tag landing pages.
- A small canonical-tag seed list at launch: `debugging`, `system-design`, `performance`, `learning`. Per-tech tags appear organically.

### Drafts (two layers)

- **`drafts/` directory** — gitignored, never published, pure local scratchpad.
- **`draft: true` frontmatter** — committed (so it syncs across machines via git) but excluded from the production build. Development server still renders it for preview. Removing the flag = publishing.

## 4. The sim-kit

The single highest-leverage investment. Distinguishes "another tech blog" from "the site engineers bookmark."

### Design principles

1. **Toys, not videos.** Reader controls all state. No autoplay-only loops.
2. **Consistent visual language.** One palette, one typography scale, one motion language. Every sim feels like part of the same product.
3. **Show your work.** Every non-trivial sim renders an `<EventLog>` so the reader can map cause to effect.
4. **Code-split.** Each sim is its own module so pages without sims pay zero JS cost for them. Docusaurus + MDX handles this automatically.
5. **Accessible by default.** Keyboard reachable, properly labeled, honors `prefers-reduced-motion`, never communicates state by color alone.

### Primitives (`src/components/sim-kit/`)

| Primitive       | Responsibility                                                                                       |
| --------------- | ---------------------------------------------------------------------------------------------------- |
| `<Stage>`       | Framed responsive canvas. Handles light/dark mode and max width.                                     |
| `<Node>`        | Labeled box/circle with `state` prop (`idle`, `active`, `failing`). Animates color/scale on change.  |
| `<Arrow>`       | Edge between two nodes. Can animate flowing dots to represent messages/requests in flight.           |
| `<Toggle>`      | Two- or three-state segmented control.                                                               |
| `<Slider>`      | Numeric input with live value display.                                                               |
| `<StepButton>`  | Fires one logical step (e.g., "Send GET"). Includes a held-down auto-fire mode.                      |
| `<Legend>`      | Color/icon meaning key, anchored to the stage.                                                       |
| `<EventLog>`    | Append-only scrolling log of structured entries. The mechanism that turns motion into understanding. |

### Simulations (`src/components/sims/`)

Each simulation composes primitives. Each is a single TSX file plus an entry in the `/playground` registry.

**V1 ships one hero sim: `<RedisReadMode />`.** Detailed below.

### Sim sandbox (dev-only)

A `/sandbox` route, gated by `process.env.NODE_ENV === 'development'`, that renders each registered sim alone for iteration. ~30 lines of code. Replaces Storybook for V1. Revisited if sim count crosses ~15.

### Testing

- Primitives: unit-tested with Vitest + React Testing Library. Covers prop variations and keyboard handling.
- Sims: not exhaustively tested; sandbox + manual interaction is the primary verification. A small smoke test per sim asserts it renders and basic controls fire events.
- CI runs `yarn typecheck` and `yarn build` only in V1. Test runs are local until the suite matures.

## 5. Worked example: `<RedisReadMode />`

The V1 hero demo. Concrete enough to validate the sim-kit API.

### What the reader sees

A `<Stage>` containing:

- One `<Node>` labeled "Client" on the left.
- One `<Node>` labeled "Master" in the upper right.
- Two `<Node>`s labeled "Replica 1" / "Replica 2" in the lower right.
- `<Arrow>`s drawn between client and each backend; arrows animate "flowing dots" during a request.
- A `<Toggle>` for `readMode`: `master` / `replica` / `replica-preferred`.
- Three controls: **Send GET**, **Auto-fire (1.5s)**, **Reset**.
- An `<EventLog>` below the stage.

### Reader interactions

- Toggling `readMode` immediately changes routing of the next read.
- **Send GET** fires one read: arrow animates, destination node briefly highlights, event log appends.
- **Auto-fire** schedules a request every 1.5s until toggled off.
- **Reset** clears the log and returns all nodes to idle.

### State machine

```ts
type Mode = 'master' | 'replica' | 'replica-preferred';
type NodeState = 'idle' | 'active' | 'down';

interface SimState {
  mode: Mode;
  master: NodeState;
  replicas: NodeState[];           // length 2
  events: LogEntry[];
  inFlight: { from: string; to: string; opId: string }[];
  autoFire: boolean;
}
```

Logic lives entirely inside the component; no global store.

### Page that embeds it

A new doc page at `docs/redis/read-modes.mdx` containing:

- Intro prose explaining why read modes exist (latency vs staleness tradeoff).
- The embedded `<RedisReadMode initialMode="master" />`.
- Follow-up prose explaining what the reader is seeing.
- A reflection prompt: "Try flipping to replica with auto-fire on — what changes?"
- A "When to use which mode" reference table.

### Stretch (V1.1, not in V1 scope)

- Click a replica node to "fail" it; observe routing fall back to master.
- Add an artificial replication lag indicator so SET → GET staleness is visible.

## 6. Authoring workflow

### Daily loop

1. `yarn start` — local dev server with hot reload.
2. Edit `.md`/`.mdx`. Site reloads in <1s.
3. Commit when a section feels durable.
4. `yarn deploy` when ready to publish.

### `yarn new` scaffolding (script at `scripts/new.mjs`)

```bash
yarn new doc kafka/consumer-rebalancing   # docs/kafka/consumer-rebalancing.mdx
yarn new post that-time-redis-evicted-us  # blog/2026-05-13-that-time-redis-evicted-us.mdx
yarn new sim KafkaPartitions              # src/components/sims/KafkaPartitions.tsx + sandbox entry
```

Each variant stamps a frontmatter template (title, date, tags, `draft: true`) and opens the file in `$EDITOR` if set.

### Personal discoverability

- `docs/intro.mdx` — a personal cockpit listing the few pages I revisit most. Written for me, not visitors.
- Local search across docs + blog means recall is fast even as content grows.

## 7. Information architecture details

### Stable URLs

- All current/future page paths are considered permanent.
- The client-redirects plugin is installed at launch so that any future reorganization can re-route old paths without 404s.
- File names use kebab-case slugs. No emoji, no spaces, no uppercase.

### Landing page

Three sections, top to bottom:

1. Hero: site name, tagline, primary CTA ("Try a simulation" → scrolls to or links to the hero sim).
2. Featured sims: 3–4 cards. Each card thumbnail is a small live inline sim, not a static image.
3. Recent blog posts: latest 3 entries with title, date, tags, excerpt.

### `/playground` page

Grouped by concept area, not by date:

- Caching, Streaming, Concurrency, Networking, Storage, etc.

Each card links to the page where the sim is embedded. Adding a sim to the playground = appending one entry to a TypeScript registry array.

### Per-page metadata

Every page renders:

- Title, last-updated date (from git mtime, auto), reading time (blog only).
- Open Graph + Twitter Card tags via Docusaurus's `themeConfig.metadata` defaults.

## 8. Performance and accessibility

### Performance budget

- Sim-less doc page: <100 KB JS first load.
- Framer Motion footprint (~30 KB gzipped) is acceptable.
- No third-party fonts, no chat widgets, no analytics scripts in V1.
- Each sim is loaded only on pages that import it (automatic code-splitting via MDX imports).

### Accessibility checklist (V1)

- Every primitive renders correct ARIA roles and labels.
- Keyboard reachable: all controls usable without a mouse.
- State changes also use shape/icon/label, not color alone.
- `prefers-reduced-motion` honored: Framer Motion variants short-circuit to fade or no-op when the user prefers reduced motion.

## 10. Risks and open questions

| Risk / question | Mitigation |
| --- | --- |
| Sim-kit API gets locked in too early and the second sim wants different primitives. | Build the hero sim first, defer formalizing the API until the second sim is in progress. Refactor at sim #2, not sim #1. |
| Authoring friction creeps in over time (e.g., MDX imports become tedious). | `yarn new` scaffolding from day one. Revisit at the 3-month mark. |
| Site becomes a graveyard of half-written notes. | The `drafts/` workflow keeps unfinished work off the public site without losing it. Sparse public content is acceptable when each piece is good. |
| GitHub Pages base-URL footguns (sub-path vs custom domain) cause broken asset links later. | Use Docusaurus's `baseUrl` correctly from the start; test a build before first deploy. |
| Performance regresses as sim count grows. | Code-splitting per sim, plus a periodic Lighthouse check (added to "future work"). |
